# 简历-职位-课程匹配模块规划

## 1. 目标

当前模块建议聚焦成一句话：

> 学生上传简历后，系统自动解析其技能、项目、证书和已学课程，再与岗位库中的职位要求和推荐课程进行匹配，输出岗位匹配度、课程支撑度、能力差距和补齐建议。

这个方向比单独做“课程-岗位映射”更容易演示，也更符合当前项目已有代码。

## 2. 当前代码现状

当前项目已经有一些可复用基础：

- `data/IT岗位数据.xlsx`：已有 674 条岗位数据，字段完整。
- `scripts/import_it_jobs_from_xlsx.py`：已有岗位 Excel 导入脚本雏形。
- `app/services/llm_ability_match_service.py`：已有 AI 双向岗位匹配服务。
- `app/services/ability_match_service.py`：已有关键词兜底匹配逻辑。
- `app/services/resume_optimizer_service.py`：已有简历文本上传解析入口，但目前主要支持 `txt / md / csv`，PDF 还没有真正解析。
- `/resume/optimize`：已有简历上传页面，但现在主要用于简历优化，不是岗位匹配主入口。
- `/job/match`：已有岗位匹配页面，但现在主要基于学生手动填写的信息，不是直接基于上传简历。

结论：

> 现在不需要推倒重做，应该把“简历上传”和“岗位匹配”两条已有链路打通。

## 4. 推荐主流程

推荐页面流程如下：

```text
学生进入“简历岗位匹配”页面
        ↓
上传 PDF / Word / txt 简历，或粘贴简历文本
        ↓
系统抽取简历文本
        ↓
系统识别：
  - 技能
  - 项目经历
  - 证书
  - 已学课程
  - 目标岗位方向
        ↓
读取 MySQL 中的岗位数据
        ↓
对每个岗位计算：
  - 技能匹配度
  - 项目匹配度
  - 课程支撑度
  - 证书匹配度
  - 学历/方向适配度
        ↓
输出 TOP5 岗位
        ↓
展示：
  - 为什么匹配
  - 已匹配技能
  - 已支撑课程
  - 待补齐课程
  - 推荐学习路径
```

## 5. 数据来源设计

第一阶段使用三类数据。

### 5.1 岗位数据

来源：`data/IT岗位数据.xlsx`

字段：

```text
job_name
company_name
hiring_city
educational_requirements
required_skills
related_projects
recommended_courses
recommended_certificates
salary_range
```

导入到 MySQL 的 `job_knowledge_records` 表中。

建议保留这些扩展字段：

```text
company_name
hiring_city
educational_requirements
salary_range
```

这样岗位匹配结果可以展示真实公司、城市和薪资，答辩时更有说服力。

### 5.2 简历数据

来源：学生上传的 PDF / Word / txt 简历。

需要抽取：

```text
姓名
专业/学历
技能
项目经历
证书
已学课程
目标岗位
简历全文
```

建议后续新增或保留 `resume_records` 表，用于保存简历解析结果，方便追溯。

### 5.3 课程数据

第一阶段不强依赖学校培养计划。

课程来源先用两部分：

```text
1. 简历中出现的“主要课程 / 相关课程”
2. 岗位数据中 recommended_courses 字段
```

学校培养计划后期上传后，再作为更权威的课程库接入。

临时课程数据如果必须使用，要明确标记为：

```text
临时模拟数据 / 待学校培养计划替换
```

不要伪装成真实培养计划。

## 6. 匹配算法建议

第一阶段建议使用可解释评分，不要一开始完全依赖大模型。

岗位总匹配度：

```text
岗位匹配度 =
技能匹配度 × 45%
+ 项目匹配度 × 20%
+ 课程支撑度 × 20%
+ 证书匹配度 × 10%
+ 学历/方向适配度 × 5%
```

课程支撑度：

```text
课程支撑度 =
简历已学课程 与 岗位推荐课程 的覆盖比例
```

例子：

```text
简历课程：
数据结构、数据库系统概论、计算机网络、操作系统、Java程序设计

岗位推荐课程：
Java程序设计、数据库原理、软件工程、计算机网络

已支撑课程：
Java程序设计、数据库原理/数据库系统概论、计算机网络

待补齐课程：
软件工程
```

这里要做同义词归一：

```text
数据库系统概论 ≈ 数据库原理
Java程序设计 ≈ Java开发基础
计算机网络 ≈ 网络协议基础
操作系统 ≈ Linux/系统基础的前置课程
```

## 7. 智能体现在哪里

答辩时可以这样解释“智能”：

### 7.1 简历语义抽取

系统不是只让学生填表，而是从简历 PDF 中自动识别技能、项目、证书和课程。

### 7.2 技能/课程同义词归一

例如：

```text
数据库系统概论 -> 数据库原理
SpringBoot -> Spring Boot
JS -> JavaScript
K8s -> Kubernetes
```

这样不是机械字符串匹配。

### 7.3 双向匹配

不只判断“学生是否适合岗位”，还判断“岗位是否适合作为学生下一阶段成长目标”。

```text
学生适岗分：当前能力能不能胜任岗位
岗位适生分：这个岗位是否适合学生补齐能力和成长
```

最终：

```text
综合匹配分 = 学生适岗分 × 60% + 岗位适生分 × 40%
```

### 7.4 可解释推荐

系统输出不是一个分数，而是：

```text
为什么推荐
哪些技能已经匹配
哪些课程已经支撑
哪些课程还缺
下一步怎么补
```

### 7.5 大模型增强

规则算法负责稳定可解释，大模型负责语义理解和推荐理由生成。

建议架构：

```text
规则算法：负责算分、兜底、可复现
大模型：负责简历语义抽取、课程归一、解释生成
```

## 9. 数据库建议

第一阶段最小可用表：

```text
job_knowledge_records      岗位库
diagnosis_records          学生诊断记录
resume_records             简历解析结果，可新增
```

如果要加强可追溯性，再加：

```text
data_sources               数据来源表
extraction_logs            抽取日志表
```

`data_sources` 用来记录：

```text
文件名
文件路径
文件 hash
来源平台
是否真实数据
是否临时模拟数据
采集时间
```

`extraction_logs` 用来记录：

```text
从哪个文件抽取
用了规则还是大模型
大模型名称
抽取结果 JSON
是否人工复核
```

## 10. 分阶段实施计划

### 第一阶段：跑通主流程

目标：能演示。

任务：

```text
1. 修复/确认 IT岗位数据.xlsx 导入 MySQL
2. 让简历上传支持 PDF
3. 新增 /resume/match 页面
4. 简历解析出技能、课程、项目、证书
5. 使用岗位库计算 TOP5 匹配结果
6. 页面展示课程支撑度和待补齐课程
```

### 第二阶段：提升智能性

目标：答辩讲得出创新点。

任务：

```text
1. 加入课程同义词词典
2. 加入技能别名词典
3. 大模型抽取简历结构化信息
4. 大模型生成推荐理由
5. 记录抽取日志，保证可追溯
```

### 第三阶段：接入学校培养计划

目标：数据更真实。

任务：

```text
1. 上传学校培养计划
2. 解析课程名称、课程目标、课程大纲
3. 建立课程-能力标签关系
4. 替换临时课程数据
5. 在页面标注课程来源
```

## 11. 当前建议不要做什么

暂时不要一上来做过重的完整知识图谱。

原因：

```text
1. 当前已有岗位 Excel 的 recommended_courses 字段，足够支撑第一版课程匹配。
2. 学校培养计划还没找到，完整课程图谱数据依据不足。
3. 比赛演示优先要跑通闭环，而不是堆表。
```

更稳的路线：

```text
先跑通：简历 -> 岗位 -> 课程匹配
再增强：课程图谱 -> 培养计划 -> 可追溯数据源
```

## 12. 最终答辩表述

可以这样说：

> 本系统以学生简历为输入，自动抽取技能、项目、证书和已学课程，并与真实招聘岗位库进行双向匹配。系统不仅计算学生与岗位的能力匹配度，还分析学生已学课程对岗位要求的支撑程度，进一步给出待补齐课程和成长路径建议。岗位数据来自真实招聘数据，课程数据在当前阶段来自简历课程与岗位推荐课程，后续可接入学校培养计划进行替换和增强。整个过程保留数据来源和抽取日志，保证匹配结果可解释、可追溯、可复核。
